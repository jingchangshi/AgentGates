### Deployment boundary -- the host-only attestation channel

`--deployment-attest` is read-only and runs no device work; the device Gate consumes its
record and may only set `deploymentVerified=true` when all seven properties hold. Each
negative below is one real way a stale or forged record could be passed off as fresh.

| test | defect | actual failing assertion |
|---|---|---|
| test_attestation_accepts_a_well_formed_fresh_record | (positive control) | "the gate has no verify_deployment_attestation, so a host-only record cannot be verified at all and deploymentVerified could only ever be asserted by hand" |
| test_attestation_refuses_a_stale_record | recorded in a previous window | same: no verifier exists |
| test_attestation_refuses_a_container_id_mismatch | record about another container | same |
| test_attestation_refuses_a_missing_device | requested card not bound | same |
| test_attestation_refuses_a_pseudo_character_node | davinci path is a regular file, so existence checks pass but nothing launches | same |
| test_attestation_refuses_a_missing_mount | container runs a different tree than claimed | same |
| test_attestation_refuses_image_drift | running image is not the contracted one | same |
| test_attestation_refuses_a_tampered_hash | record edited after the fact | same |

The seven share one reason today (no verifier). That is why
`test_reference_verifier_discriminates_every_negative` exists and PASSES: it replays all
seven against a contract reference and requires each to be refused for its own code
(`STALE`, `CONTAINER_MISMATCH`, `DEVICE_MISSING`, `NODE_NOT_CHAR`, `MOUNT_MISSING`,
`IMAGE_DRIFT`, `TAMPERED`) while the clean record is accepted. A future verifier that
simply rejects everything will fail that control.

## Tests that passed vacuously and were tightened

Recorded so nobody reads this baseline as "red by construction".

1. **word-search assertions.** Two tests asserted on SOURCE TEXT: `"workload" in source`
   passed on a docstring, `"archived" in source` passed on a comment. Both were replaced
   with behavioural checks. Suite went from **2 PASS to 0 PASS**.
2. **vacuously-true properties.** "Can the next job enter after a failure?" is true when
   no lock exists; "did the payload run once?" is true when it never came back; "is the
   directory unique?" was satisfied by the pre-existing run_id suffix. Each now fails
   loudly AND asserts the property that makes the claim meaningful (overrun actually cut
   short, record actually identifies its run).
3. **a self-repairing negative.** The first version of the tamper case recomputed the
   digest after tampering, which repaired the defect it was meant to detect. Caught by
   the discriminator control, which reported "the reference ACCEPTED the tampered_hash
   record". Fixed by excluding that case from re-digesting.
4. **a thread-unsafe harness.** The first lock tests used threads; `flock` is per open
   file description and `contextlib.redirect_stdout` is process-global, so two threads
   corrupted stdout and swallowed later results. Replaced with real competing processes,
   which also model what a second team job actually is.

## Standing test methodology: a reported green must be provably green

These are not anecdotes. Each was a real defect found in THIS suite, and each is a
rule for every test added from here. They are the same family as "a crash is not red":
the failure mode is always a report that cannot distinguish itself from success.

1. **A hardcoded injection anchor silently stops injecting.** The mutation controls
   replaced a call site by exact string. When `device_occupancy` gained the preflight
   argument the anchor no longer matched, `str.replace()` returned the source
   UNCHANGED, and both controls reported PASS -- the "injected" source was byte-for-byte
   identical to the clean one. Rule: derive the anchor FROM the source, and assert that
   the injection actually changed it (`injected != original`). A mutation control that
   cannot show it mutated something proves nothing.

2. **A mismatched stub kills the harness, and a dead harness looks like a pass.**
   Removing one stub made the tool raise an uncaught `GateError`, so it exited with
   rc=1 and printed ZERO failure lines. At a glance -- and in any summary that counts
   lines -- that is indistinguishable from a clean run. Rule: wrap the harness body and
   report an internal failure as a NAMED FAIL, never as an exception that ends the run.

3. **A crash is not a red.** A suite that aborts early silently skips every test after
   the crash, so the red count is fiction. Assert `AssertionError`-only failures, and
   treat any other exception as a harness defect to be fixed, not as a finding.

4. **A test that needs an ambient environment cannot be run by anyone else.**
   `device_policy.py` passed only two configuration keys and therefore died with
   `ENV_CANN_SCRIPT_MISSING` from a bare shell once the preflight existed. Rule: a test
   supplies its own complete minimal configuration and runs under `env -i`.

5. **Validation layers are not interchangeable.** `TF_REPO`/`CONTAINER_NAME` are
   structural and named by `load_config`; `CANN_SET_ENV` is an environment fact named by
   the preflight. Demanding all three of one layer is a wrong test, not a stricter one.
   Keep the division; do not collapse it for convenience.

6. **"It passes in my checkout" is not evidence.** Re-runs extract committed content
   with `git show <ref>:<path>` into a fresh directory and record the sha256 of the gate
   and of every test actually executed. A working tree can be mid-edit -- this baseline
   was itself once captured against a tree whose `parse_npu_smi()` had lost its return.

## Invariants the implementation must not break

- **busy is RECORDED only**: no wait, poll, retry, skip, downgrade, or busy-dependent
  card choice (device_policy.py enforces the static half; a control keeps its detector alive).
- **the team lock coordinates this team only**; another tenant being busy is metadata.
- Do not touch: busy semantics, `parse_device_list`, `environment_preflight`,
  `deployment_verify`.
- Every new mechanism needs three negatives: normal path, single defect, injected fault.

This is an IMPLEMENTATION DEFECT, reported not fixed. The section comment in
verify_attestation says "(6) the image must not have drifted", but the code only
checks that SOME digest is present:

    configured = config.get("IMAGE")
    if configured and not attestation.get("image_digest"):
        raise GateError("ATTESTATION_INVALID: no image_digest recorded", EXIT_BLOCKED)

Nothing ever compares attestation["image_digest"] against a contracted value, so an
attestation describing a completely different image verifies clean. Proven directly,
independent of the test suite, under all three plausible config spellings
(IMAGE only / IMAGE_DIGEST only / both): the drifted digest sha256:eeee... was
accepted every time.

Fix belongs to I2: compare the attested digest against the contracted image
(config IMAGE / IMAGE_DIGEST) and raise ATTESTATION_IMAGE_DRIFT on mismatch. Note
that comparing the image NAME is not enough -- docker inspect reports the image ID,
so the contract must be expressed as a digest.

1. verify_deployment_attestation -> **verify_attestation(attestation, config,
   device_ids, node_facts, observe)**; content_sha256 (not payload_sha256);
   refusal codes are the implementation's own spelling, so each negative asserts the
   code ACTUALLY raised is printed on failure. If a check fired with a different
   name, the message shows the name, so "renamed" is distinguishable from "absent".

   to match the call by SHAPE (regex), because the control is about the detector, not
   about a signature. It passes again.
3. The discriminator's reference verifier was rewritten to the real schema and the
   real codes, and now includes the image-drift rule -- which is exactly how the
   missing check was confirmed to be a defect rather than a test artifact.

## Standing methodology (keep this; it is what produced the evidence)

### 1. A crash is not a red. The harness must enforce that.

A failing test can fail three ways: the behaviour did not happen (useful), the code
crashed (noise), or the assertion was never reached (a lie). "N red" says nothing
until you know which. So the runner parses every FAIL line and REJECTS any failure
whose exception type is not AssertionError; the report states the count explicitly
and it must be 0.

This is not theoretical. During the eb00028 update the discriminator referenced a
helper deleted in a rewrite and raised NameError. Without the check it would have
been counted as "one more gap"; with it, it was immediately visible as a crash --
a defect in the TEST, not evidence about the product. It was fixed and the run
returned to 0 non-AssertionError failures.

Corollary: a message must say what did NOT happen ("the gate has no team lock lease,
so two jobs can enter the payload concurrently"), never merely "assert False" or a
bare AttributeError. The failure text is the finding.

### 2. A suite that can only go red proves nothing.

Every negative needs a control that can go green, or the baseline is unreadable:
"all red" cannot distinguish "feature missing" from "harness broken". Hence the
control group -- busy-is-recorded, injected-busy-skip-is-detected -- which passes
today and must keep passing.

### 3. Negatives that share one failure reason prove only that the reason is missing.

When seven attestation negatives all failed for "no verifier exists", they showed
the mechanism was absent but said NOTHING about whether the matrix would catch each
defect once a verifier landed: a verifier that refuses EVERYTHING satisfies them all.
The discriminator control replays the same defects against a contract reference and
requires each to be refused for its OWN code, with the clean record accepted.

This is what turned a shrug into a finding. With the reference in place it reported
"the reference ACCEPTED the image_drift record" -- which is how a MISSING CHECK was
told apart from a MISTAKEN TEST, and how the real image-drift defect (reported to I2,
not fixed here) was confirmed rather than assumed. It also caught a tamper case that
recomputed the digest it existed to detect.

The discriminator is PERMANENT. Do not delete it to make a revision go green: it is
the only thing standing between "refuses everything" and "refuses the right things".

### 4. An interface name is not a contract; the DEFECT is the contract.

When the implementation landed with verify_attestation / content_sha256 / its own
refusal-code spelling, the tests were adapted to the real API. That is not a
relaxation: each negative still asserts that its specific defect is refused, and the
failure message prints the code ACTUALLY raised, so "renamed code" stays
distinguishable from "absent check". Never weaken an assertion to reach green --
adapt the call, keep the property.

### 5. Complementary: prove the record is about THIS container.

"unlinked mount" (ATTESTATION_MOUNT_NOT_LINKED) is kept alongside the container_id
check. Inside the container the docker ID is unreadable, so an ID comparison cannot
carry the identity burden there; but an attested mount that is absent in here proves
the record describes a different container. The two checks cover each other's blind
spot, which is why both are negatives rather than one being "enough".
