The container timeout sends TERM then allows 15 seconds before KILL. The outer timeout remains larger. Nonzero exits, interruption and timeout never become PASS. The source must have a configured `build/build.ninja`; gates do not configure a fresh build tree. The one exception is Ascend's from-zero branch, which `ascend-build` and `ascend-build-host` take when the build directory holds neither `build.ninja` nor `CMakeCache.txt`; the matching regression gates still run an existing tree only. `tilelang-npu` is a second exception and a different one: it is host-local and configures its own tree on every run, because the point of that Adapter is to prove an ordinary TileLang checkout builds from source on this host rather than to reuse a tree something else produced.

`ascendnpu-ir` ships the same Gate twice: once through Docker and once on the host. The host pair is `ascend-build-host` / `ascend-regression-host`; the two host recipes run `scripts/host_gate.py`, which imports and binds the pinned sibling `scripts/docker_gate.py` and so uses its parser, three-state build-tree probe, `timeout --signal=TERM --kill-after=15` chain and from-zero full-build command unchanged. Docker transport is the only omission, and it is a real one: no container identity, no bind-mount mapping, no device/inode comparison and no `docker exec` prefix, because on the host the tree is the source root and the identity proof has nothing left to prove. In exchange the host route checks what Docker mode inherits from its image and never inspects: `ninja >= 1.12` (`CMakeLists.txt:6-13`), `cmake >= 3.28` (`CMakeLists.txt:2`), the presence of `bash`, `timeout`, `nproc`, `clang`, `clang++`, `g++`, `python3`, `ld.lld` and `git` on the effective PATH, a git work tree, and - only for a from-zero tree - executable `ccec` and `llvm-link` plus populated `third-party/llvm-project` and `third-party/shmem`. The two routes are independent in the manifest: neither gate depends on the other, so `run --all` now covers both and a host-only operator names `--gate ascend-build-host --gate ascend-regression-host`.

A host configuration refusal exits 2 (`BridgeError`), the same code Docker mode uses. Inside the generated script the coding is the shared generator's, not a new one: a from-zero build failure or an inner timeout is wrapped by its `fail` and exits 3 (`docker_gate.py:666-668`), while the incremental path preserves `timeout`'s 124. Neither recipe declares `blockedExitCodes`, and none of these codes should be read as a general "blocked" claim.

The host regression configuration check exits 0 on a machine with no build tree at all - that is the normal state of a new host, and `doctor` must be able to say so - and only reports the missing `build.ninja`. The regression recipe still refuses a from-zero tree.

## Machine configuration

Keep machine files outside the package and pass an absolute `--env-file`. Files contain strict `NAME=value` data, comments and blank lines. Balanced surrounding quotes are removed. Unknown keys, duplicate keys and malformed lines fail. The gate readers never execute the file or expand substitutions. On the Docker route CANN and Conda paths name locations inside the container; on the Ascend host route the same keys name host paths. CANN is initialized before Conda; Conda setup and environment must be supplied together.

`bska-npu` is host-local and has no container route. Its `BSKA_NPU_CANN_SETUP`, `BSKA_NPU_CONDA_ENV`, `BSKA_NPU_CONDA_ENVS_PATH`, `BSKA_NPU_CANNBENCH_REPO`, `BSKA_NPU_CANNBENCH_TASK` are required; `BSKA_NPU_CANNBENCH_ARCH`, `BSKA_NPU_BUILD_SUBDIR`, `BSKA_NPU_NODE_BIN`, `BSKA_NPU_CLAUDE_BIN` and `BSKA_NPU_TRITON_ASCEND_VERSION` are optional. An empty `BSKA_NPU_TRITON_ASCEND_VERSION` is refused rather than skipped: without it the Adapter cannot prove the triton_ascend build is the reviewed one.

`--env-file` maps to `ASCENDNPU_ENV_FILE` for Ascend, `TILELANG_HIVM_ENV_FILE` for both HIVM TileLang adapters, `TILELANG_NPU_ENV_FILE` for the host-local TileLang adapter, `TLA_NPU_ENV_FILE` for the TLA adapter, `FK_ASCEND_ENV_FILE` for the ForgeKernel adapter, `BSKA_NPU_ENV_FILE` for BSKA and `TILEFOUNDRY_NPU_ENV_FILE` for TileFoundry. Without an explicit selection, bridges look beside the packaged adapter template, retaining the legacy owning-checkout search for installed pack compatibility. They never search a user's home for machine files. An explicitly selected missing file fails.

Ascend permits `ASCENDNPU_CANN_SETUP`, `ASCENDNPU_CONDA_SH`, `ASCENDNPU_CONDA_ENV`, optional `ASCENDNPU_CCEC_BIN`, the container identity `ASCENDNPU_CONTAINER_NAME` / `_USER` / `_HOME`, `ASCENDNPU_CONTAINER_SOURCE`, and the build selection `ASCENDNPU_BUILD_SUBDIR` / `ASCENDNPU_NINJA_JOBS`. All of them are file keys: the launching environment is not a configuration source for any adapter. `ASCENDNPU_CCEC_BIN` is needed only by the from-zero branch, and `ASCENDNPU_CONTAINER_SOURCE` confirms the container path of the checkout rather than inventing one - the bind-mount mapping is still derived and compared. Only `ASCENDNPU_GATE_TIMEOUT` remains a launch value, because it bounds an invocation rather than describing the machine.

An export that the file does not define is refused, and an export that disagrees with the file is refused, so neither a stale shell nor a stale file can silently win. Sourcing `env.sh` and then running a gate is still supported, because the export then equals the file. AgentGates resolves the same file to take its `build:<dir>` lease, so a lock on one tree cannot cover a run writing another.

The Ascend file serves both routes, and a key belongs to the route that reads it. `ASCENDNPU_CONTAINER_NAME` / `_USER` / `_HOME` and `ASCENDNPU_CONTAINER_SOURCE` are Docker-route only: the host route reads none of them, so a host-only machine leaves them empty and its configuration check still passes. `ASCENDNPU_CANN_SETUP`, `ASCENDNPU_CCEC_BIN`, `ASCENDNPU_BUILD_SUBDIR` and `ASCENDNPU_NINJA_JOBS` are read by both, as container paths on the Docker route and as host paths on the host route. One file can therefore serve both routes only while its paths are meaningful in both, which a `/home:/home` mount usually makes true; otherwise the supported arrangement is two files selected by `ASCENDNPU_ENV_FILE`.

`ascend-build` selects its mode from the build directory inside the container: `build.ninja` present means incremental Ninja, neither `build.ninja` nor `CMakeCache.txt` means a from-zero full build through the pinned `scripts/full-build.sh` followed by product checks, and `CMakeCache.txt` without `build.ninja` is refused. The full build never deletes a tree, refuses `-r`/`--rebuild`, and never overwrites an existing `build.log`. `ascend-regression` runs an existing tree and carries no full-build branch.

TileLang's shared file permits:

- `TILELANG_HIVM_CONTAINER_NAME`, `TILELANG_HIVM_CONTAINER_USER`, `TILELANG_HIVM_CONTAINER_HOME`, `TILELANG_HIVM_CONTAINER_SOURCE`;
- `TILELANG_HIVM_CANN_SETUP`, `TILELANG_HIVM_CONDA_SH`, `TILELANG_HIVM_CONDA_ENV`, `TILELANG_HIVM_CONDA_ENVS_PATH`;
- `TILELANG_HIVM_HIVM_COMPILER`, `TILELANG_HIVM_HIVM_TARGET`;
- the build selection `TILELANG_HIVM_BUILD_SUBDIR`, `TILELANG_HIVM_NINJA_JOBS`;
- manual provisioning keys `TILELANG_HIVM_WHEEL_DIR`, `TILELANG_HIVM_PIP_INDEX`, `TILELANG_HIVM_PYTHON_VERSION`, `TILELANG_HIVM_SOURCE_ROOT`.

The file's container identity overrides stale launching exports, and `TILELANG_HIVM_CONTAINER_SOURCE` follows the same rule: it confirms the container path of the checkout when that differs from the derived bind-mount mapping, and because the mapping is still computed and compared, the key can confirm a path but never invent one. The NPU gate accepts the user key but runs as root, preserving the upstream `uda_occupy_dev_by_ns` workaround. A configured HIVM compiler must be an absolute executable container path. Its optional target can only be `Ascend950PR_9579`; compiler and target are explicitly forwarded as `HIVM_COMPILER` and `HIVM_TARGET`.

The host-local TileLang adapter owns `TILELANG_NPU_` and its own file, deliberately separate from the two HIVM adapters: it shares no container, no HIVM compiler and no build directory with them, so sharing their file would let one Adapter's lease describe another Adapter's tree. Its file permits `TILELANG_NPU_CANN_SETUP`, `TILELANG_NPU_CONDA_SH`, `TILELANG_NPU_CONDA_ENV`, `TILELANG_NPU_CONDA_ENVS_PATH`, `TILELANG_NPU_PYTHON`, `TILELANG_NPU_CMAKE_BIN`, `TILELANG_NPU_BUILD_SUBDIR`, `TILELANG_NPU_NINJA_JOBS` and `TILELANG_NPU_EXAMPLE_TESTS`. `TILELANG_NPU_CMAKE_BIN` is a machine fact rather than a convenience: an existing build tree is regenerated by the CMake that wrote it, and this host's conda environment ships a different major version from the system one, so the operator names which binary regenerates the tree. `TILELANG_NPU_EXAMPLE_TESTS` is a reviewed comma-separated list of example test files rather than a glob, so the regression cannot silently widen as examples are added. Its device id is a launch value, not a file key.

Unlike every other Adapter here, this one writes its own build tree: its build gate runs CMake configure before Ninja with `-DSKBUILD_SABI_COMPONENT=Development.SABIModule -DSKBUILD_SABI_VERSION=3.9`, drops any stale `tilelang_*.cpython-*.so`, verifies `libtilelang.so` plus all four `*.abi3.so` Cython extensions, and writes `<build>/.agent_gates_build_stamp.json` (recording `gitHead` and `nativeInputsSha256`). Downstream consumers (`forgekernel-ascend-npu` and `tilefoundry-npu`) across Python >= 3.10 reuse that build tree read-only instead of rebuilding TileLang themselves. An incremental re-run reuses the same directory; the gate never deletes a tree.

The host-local TLA adapter runs directly on the host as the invoking user (container execution is quarantined; see [docker-mode-quarantine.md](docker-mode-quarantine.md)) and owns the `TLA_NPU_` prefix and its own file. It permits `TLA_NPU_CANN_SETUP`, `TLA_NPU_CONDA_SH`, `TLA_NPU_CONDA_ENV`, `TLA_NPU_CONDA_ENVS_PATH`, `TLA_NPU_PYTHON_VERSION`, provisioning keys `TLA_NPU_WHEEL_DIR`, `TLA_NPU_TRITON_WHEEL`, `TLA_NPU_PIP_INDEX`, `TLA_NPU_BUILD_SUBDIR`, and legacy compatibility keys `TLA_NPU_CONTAINER_NAME` / `_USER` / `_HOME` / `_SOURCE` (accepted by the parser but ignored on host execution). Two of its keys name its two inputs, which are different directories: `--source` is the triton-ascend checkout whose TLA implementation is under test, and `TLA_NPU_TEST_DIR` holds the test (`test_tla.py`) that exercises it. A third, `TLA_NPU_CACHE_DIR`, names a parent directory outside both, under which each run allocates a fresh temporary subdirectory for `TRITON_CACHE_DIR` so the cache never collides with hashed inputs or stale runs. It is a device adapter, so it also requires an explicitly authorized device through `--device-id` or `TLA_NPU_DEVICE_ID`, takes an `npu:<id>` lease on it, and resolves `TLA_NPU_REQUIRE_EXCLUSIVE_DEVICE` when the local configuration sets the exclusivity policy - the engine forwards that policy into the variable each device adapter actually parses, rather than one hardcoded variable. `TLA_NPU_BUILD_SUBDIR` exists because the engine resolves a build directory for every adapter; this adapter writes no build tree, so it declares no job count. Unlike the TileLang gates, it does not require `build/build.ninja`: its source root is the triton-ascend checkout, so provenance is that checkout's Git identity (`git-files` mode, head plus file hash) rather than a build tree. The receipt also records the identity of the installed TLA implementation (a hash over `triton/language/extra/tla/*.py` plus the imported `triton` version), because the wheel actually executed is not the checkout under test and a version string alone cannot distinguish a wheel rebuilt at the same version.

The TLA adapter gates on what the process that ran the test actually measured: at least one tensor constructed on the device, a positive peak device allocation, and at least one kernel image in a fresh `TRITON_CACHE_DIR` (the Ascend backend emits `.npubin`; a `.o` is counted but not required, because requiring an artifact the backend never writes would be unsatisfiable rather than strict). The synchronization result, the two output markers and the script exit status are also gated, so a stub that prints the markers but never reaches the kernel still fails.

It does **not** claim to re-derive which physical board ran. The device UUID and name are recorded in the receipt but explicitly not gated: on this host both cards report the same UUID, and the visible-device echo is a value the adapter itself exported, so gating on either would be a tautology rather than evidence. `acl.rt.get_phy_dev_id_by_logic_dev_id` is likewise not used, because it answers from the host physical table regardless of which card `ASCEND_RT_VISIBLE_DEVICES` selected; `npu-smi info` is queried on the host to resolve physical/NPU ID mapping and exclusivity checks. What the gate proves is that a compiled TLA kernel ran on the one card the operator named by `--device-id`, not that AgentGates independently re-identified that board.

The TileFoundry adapter (`tilefoundry-npu`) is host-local and owns the `TILEFOUNDRY_NPU_` prefix (`agent_gates/adapters/tilefoundry-npu/scripts/tilefoundry_host_gate.py`). Its machine file permits `TILEFOUNDRY_NPU_CANN_SETUP`, `TILEFOUNDRY_NPU_CONDA_SH`, `TILEFOUNDRY_NPU_CONDA_ENV`, `TILEFOUNDRY_NPU_CONDA_ENVS_PATH`, `TILEFOUNDRY_NPU_PYTHON`, `TILEFOUNDRY_NPU_TILELANG_SOURCE`, `TILEFOUNDRY_NPU_TILELANG_BUILD`, `TILEFOUNDRY_NPU_CPU_TESTS`, `TILEFOUNDRY_NPU_DEVICE_TESTS`, `TILEFOUNDRY_NPU_BUILD_SUBDIR`, the CANNBench keys (`TILEFOUNDRY_NPU_CANNBENCH_REPO`, `TILEFOUNDRY_NPU_WORK_ROOT`, `TILEFOUNDRY_NPU_CANNBENCH_ARCH`, `TILEFOUNDRY_NPU_CANNBENCH_TARGETS_FILE`, `TILEFOUNDRY_NPU_CANNBENCH_TARGETS`), and optional agent/reference keys (`TILEFOUNDRY_NPU_LLM_BACKEND`, `TILEFOUNDRY_NPU_AGY_BIN`, `TILEFOUNDRY_NPU_AGY_EXPLOIT_MODEL`, `TILEFOUNDRY_NPU_AGY_EXPLORE_MODEL`, `TILEFOUNDRY_NPU_AGY_COMMON_ARGS`, `TILEFOUNDRY_NPU_AGY_MAX_CONCURRENCY`, `TILEFOUNDRY_NPU_TILELANG_REPO`, `TILEFOUNDRY_NPU_CANNBOT_DSL_REPO`, `TILEFOUNDRY_NPU_OPS_TRANSFORMER_REPO`, `TILEFOUNDRY_NPU_ASC_DEVKIT_REPO`, `TILEFOUNDRY_NPU_CAMPAIGN_DEVICE_IDS`). When `TILEFOUNDRY_NPU_TILELANG_SOURCE` is set, TileLang is **reused read-only and never rebuilt** by `tilefoundry-npu`: preflight and every gate verify `libtilelang.so`, all four `*.abi3.so` extensions, and `.agent_gates_build_stamp.json` against the current native/CMake/Cython digest, failing closed with `BLOCKED_ENV` (exit 75) instructing the caller to run `tilelang-npu-build` first if native inputs changed, while prepending `<TILELANG_SOURCE>` onto `PYTHONPATH` ahead of `site-packages`. Its device id (`TILEFOUNDRY_NPU_DEVICE_ID`) and exclusivity policy (`TILEFOUNDRY_NPU_REQUIRE_EXCLUSIVE_DEVICE`) are launch/config values, never written to `env.sh`. `TILEFOUNDRY_NPU_CAMPAIGN_DEVICE_IDS` is an orchestration declaration, not a launch value: the TileFoundry campaign reads the ordered candidate cards from the machine file before submitting, while each execution still names exactly one card via `--device-id`; the Adapter parses and tolerates the key but never reads, forwards or authorizes from it, and `devices.allowed_npu_devices` remains the sole authority over which cards `submit` accepts. `tilefoundry-npu-cpu` activates the Conda environment **without** sourcing CANN (`TORCH_DEVICE_BACKEND_AUTOLOAD=0`, `TILELANG_DISABLE_CACHE=1`, `PYTHONPATH` over `src:targets/ascend:targets/apple:targets/nvidia`) so `ortools` and CANN native libraries do not collide, and runs `pytest` over `TILEFOUNDRY_NPU_CPU_TESTS` (default when empty: `tests/tilefoundry,tests/ascend/target,tests/ascend/ir,tests/ascend/passes,tests/ascend/operators`) with JUnit XML verification. `tilefoundry-npu-device` depends on `tilefoundry-npu-cpu` and uses a `deviceWindow` (`waitSeconds: 60`) lease: it sources CANN `set_env.sh` + Conda `tilefoundry-npu`, runs an in-process NPU runtime & compute probe (`import tilefoundry`, optional live reused-`tilelang` check, FP32 vector add, BF16 Cube `matmul`, device allocation > 0, `torch.npu.synchronize()`), and — only when `TILEFOUNDRY_NPU_DEVICE_TESTS` is non-empty — additionally runs `pytest` over those relative paths inside the same lease window. Both `TILEFOUNDRY_NPU_CPU_TESTS` and `TILEFOUNDRY_NPU_DEVICE_TESTS` accept comma- or whitespace-separated relative paths under `--source` (no leading `/` or `..`), verified during `--check-config` / `doctor`.
The ForgeKernel adapter is host-local and owns the `FK_ASCEND_` prefix. Its smoke gate is deliberately cheap to configure — it needs only the interpreter and a per-run device id — so a device can be proved usable before any ForgeKernel or TileLang build exists. Its file permits `FK_ASCEND_CANN_SETUP`, `FK_ASCEND_PYTHON`, `FK_ASCEND_TILELANG_SOURCE`, `FK_ASCEND_TILELANG_BUILD`, `FK_ASCEND_TILELANG_CACHE_DIR`, `FK_ASCEND_WORK_ROOT`, `FK_ASCEND_BUILD_SUBDIR`, `FK_ASCEND_VENV`, `FK_ASCEND_PIP_INDEX`, `FK_ASCEND_DEPENDENCY_POLICY`, and the agent keys `FK_ASCEND_CLAUDE_BIN`, `FK_ASCEND_PROVIDER_ENDPOINT`, `FK_ASCEND_PROVIDER_MODEL`, `FK_ASCEND_PROVIDER_KEY_VARIABLE`, `FK_ASCEND_AGENT_SANDBOX`, `FK_ASCEND_AGENT_NETWORK`. Its device id is `FK_ASCEND_DEVICE_ID` and, like every device adapter's, it is a launch value rather than a machine key. TileLang is a REUSED dependency here: the adapter verifies the existing checkout and its `libtilelang*.so` and records their digests, and never configures, compiles or pip-installs TileLang. The build installs with `--no-deps` into a `--system-site-packages` venv, so the shared toolchain another run depends on is not upgraded. The provider API key is never a file key: the file names the environment variable that holds it.

## Device leases

A device adapter names a card and leases `npu:<id>`; the id is always explicit, because an omitted id is a refusal rather than a default. The lease coordinates AgentGates runs with each other. It cannot exclude other tenants of a shared machine, and no reading of a receipt should treat it as if it did.

The lease is taken for the whole recipe unless the recipe declares a window. A recipe with `"deviceWindow": {"waitSeconds": N}` opens the lease itself, around the work that actually drives the card, and the engine holds nothing: the engine passes the lease path, the resource name and the wait bound in `AGENT_GATES_DEVICE_LEASE_PATH` / `_RESOURCE` / `_WAIT_SECONDS`, and the recipe flocks that exact file. Handing over the path rather than re-deriving it is deliberate — the lease file is a hash of the resource name, and a second implementation of that hash is how two locks get taken on one card.

The two modes cannot mix inside one run. Holding the lease while handing the same lease to a child deadlocks on the lock the child waits for, so an adapter that declares both kinds of device recipe is refused as a manifest error instead of running one of its gates unprotected.

A window waits for at most its declared bound and then exits 75, which the runner records as `BLOCKED_ENV`: a resource refusal where nothing ran, never a failed test. An occupied card produces no such refusal. Occupancy is measured and recorded as `free`, `shared(n)` or `unknown` — a count only, never another tenant's process id or command line — and it is never gated, because on a shared machine another user's process is the normal case. A windowed gate that reports no window is `INVALID_EVIDENCE`: an unshown window is not a short one. The one exception is a gate the Adapter classified `BLOCKED_ENV`: it ran nothing, so there is no window to show, and it is recorded as a window that never opened rather than upgraded to bad evidence.

A window should cover work, not setup. On a host where importing the backend and creating the device context takes tens of seconds, an Adapter warms up first and takes the lease afterwards; the receipt then carries the split (`warmupSeconds` outside, `heldSeconds` / `probeSeconds` inside) so the claim is checkable. Those durations are recorded and never gated, because a slow machine is not a failed test. The engine caps a reported window whose resource or path differs from the one it granted, whose end precedes its start, or whose occupancy is not a defined value.

## Commands and checks

```bash
agent-gates list --json
agent-gates doctor --adapter tilefoundry-npu --source /absolute/source --env-file /absolute/machine.env --device-id 1 --json
agent-gates run --adapter tilefoundry-npu --source /absolute/source --env-file /absolute/machine.env --device-id 1 --all --json
agent-gates verify --run-id RUN_ID --json
agent-gates report --run-id RUN_ID --json
```

Docker bind mounts determine the container source path. The host recipes take the source root as given and derive nothing. The most specific bind wins; missing or equally specific conflicting mappings fail. The bridge compares host/container source device and inode before execution. Core evidence also binds source identity, adapter manifest and script digests, executable, configuration, process logs and discovered artifacts. Verification determines whether a recorded result is still current.

TileLang regression runs exactly `testing/ascend/target/test_tilelang_ascend_target.py` and `testing/ascend/cache/test_tilelang_ascend_binary_cache.py`. JUnit supplies collected, passed and skipped counts. A positive collected count, at least one non-skipped test, native-library presence and host/container module/native SHA256 agreement are required. These are host regression checks; they do not establish complete HIVM code generation or device correctness.

The separate NPU adapter requires an explicitly allocated device, using CLI `--device-id ASSIGNED_ID` or `TILELANG_HIVM_DEVICE_ID`. Neither an idle card nor visibility authorizes selecting it. On top of that declaration the Adapter performs a read-only Host probe with `npu-smi info` and refuses to dispatch when the card already holds any process the Gate did not start, or when the driver cannot be read at all: a missing binary, a non-zero exit, a timeout or an unrecognised answer is treated as unknown occupancy, not as free. The probe maps the authorized physical id through the `npu-smi` mapping table rather than assuming NPU ID equals physical id, runs both in `--check-config` and again immediately before the container command, and reports only the holder count. It never selects, resets or retries a card, and it cannot see a job that starts after the probe; shared-machine scheduling remains the operator's responsibility. It requires measured tensor movement, numerical assertions, positive device allocation, matching authorized physical-device mappings before and after, collected passing tests and successful synchronization. The scope is fixed SIMD vector-add sanity. Running `--all` on the base adapter never invokes this gate.

## Manual support and provenance
